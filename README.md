# Price Intelligence

Телеграм-уведомления о настоящих скидках в магазинах кроссовок и стритвира.
Бот обходит список магазинов, запоминает цены и присылает сообщение с фотографией
товара, когда цена реально падает.

<b>New Balance</b>
991v2 Made in UK
Размер: UK 8.5 · SKU 003381070

💰 <b>$164</b> (в других магазинах $301, по 6)
📉 Минимум за всё время наблюдения

🏪 Footpatrol UK (GB) · в магазине £120.00
🕐 цена упала 4 ч назад

🔗 https://www.footpatrol.com/products/678510
</pre>

## Что считается скидкой

Зачёркнутая цена в магазине — это маркетинг, а не факт, и это единственный
сигнал, который ничего не стоит нарисовать. Поэтому «было» берётся из четырёх
источников, в порядке того, насколько трудно их подделать, и собственный ярлык
магазина стоит последним:

1. **Минимальная цена, которую сам магазин реально держал за 30 дней до
   падения.** Это формула директивы ЕС 98/6/EC, и она ровно про этот случай:
   поднять 200 до 300 на неделю и вернуть 200 — значит оставить месячный минимум
   на 200, то есть скидка равна нулю. Если цена не опустилась ниже собственного
   недавнего дна, магазин её не снижал, что бы ни было написано на ярлыке.
2. **Что просят за ту же вещь другие магазины прямо сейчас.** Товары
   сопоставляются по артикулу производителя, который переживает любые названия:
   `CW2288-111` есть в четырнадцати магазинах списка. Истории для этого не нужно
   вовсе — а её почти и нет: 2 749 975 вариантов из 2 762 842 видели ровно раз.
3. **Рекомендованная цена как мода зачёркнутых цен многих магазинов.** Настоящую
   RRP показывают все; выдуманную — только тот, кто её выдумал. Ярлык выше
   рекомендованной больше чем на `inflated_tag_pct` эталоном не становится.
4. **Ярлык самого магазина** — и только от магазина, который себя не
   дисквалифицировал.

Плюс два вето. Цена выше того, что просят другие магазины, скидкой не является,
от чего бы её ни отсчитывали. И зачёркнутые цены магазина не считаются
доказательством ничего, если магазин **считает скидки по правилу, а не помнит
прежнюю цену**.

Последнее видно по форме распределения. Настоящая прежняя цена даёт тот процент,
который даёт арифметика, — 36.4%, 22.8%, 41.1%, — и попадает на круглую ступень
в 5% примерно настолько часто, насколько позволяет случай. Замер по 78 магазинам
с достаточным числом ярлыков:

| Магазин | Ярлык на каталоге | Из них круглых |
|---|---|---|
| www.wannastyle.com | 84% | **100%** |
| it.oneblockdown.it | 64% | **100%** |
| www.sneakersnstuff.com | 62% | **90%** |
| … медианный магазин | | 55% |
| www.footpatrol.com | 38% | 21% |
| www.overkillshop.com | 45% | 16% |

Магазин на 100% не помнит, сколько вещи стоили. Он применяет «−40% на эту
категорию», а «было» получается из арифметики. Таких в списке 16 из 149.

Отдельно: если зачёркнутая цена не менялась дольше `fake_sale_days`, это обычная
цена с украшением, и оценка режется.

Уведомление уходит, только когда сошлось всё сразу: процент скидки, абсолютная
экономия в долларах (20% от футболки за $30 — не новость), наличие на складе — и
не больше `max_alerts_per_store` штук из одного магазина, чтобы одна распродажа
не занимала весь прогон.

Один и тот же артикул, подешевевший сразу в нескольких магазинах, — это одна
новость, а не три. Уведомления по нему сводятся в одно, с лучшим предложением, и
в сообщении говорится, сколько магазинов ещё его продают. Исключение — товары из
`data/watchlist.txt`: за ними следят поимённо, и они приходят независимо от
порогов (но не в обход вето — эталон всё равно должен откуда-то взяться).

## Установка

```bash
git clone https://github.com/Whyslab/price-intelligence
cd price-intelligence

python -m venv .venv
source .venv/bin/activate
pip install -e .

cp .env.example .env              # вписать токен бота и chat id
cp filters.toml.example filters.toml   # настроить бренды, размеры, пороги
```

Токен бота даёт [@BotFather](https://t.me/BotFather), свой `chat_id` — 
[@userinfobot](https://t.me/userinfobot).

Зависимости: Python 3.11+, `httpx`, `python-dotenv`. База — SQLite, ставить
ничего не нужно.

## Первый запуск

```bash
python -m pi sites          # загрузить data/sites.txt в базу
python -m pi detect         # определить, как читается каждый магазин
python -m pi run --collect-only   # собрать цены, ничего не присылая
python -m pi reindex        # разобрать артикулы и размеры для сравнения магазинов
python -m pi seed           # объявить текущие распродажи «уже виденными»
python -m pi run            # дальше — только новые падения цены
```

Шаг `seed` пропускать не стоит. Магазины держат распродажи месяцами, и на
реальной базе из 169 магазинов порогам сразу удовлетворяли **29 853 товара**.
Это не новости, а состояние витрин на момент запуска. Без `seed` они бы шли
по `max_alerts_per_run` за прогон — месяцами. Проверить, сколько их у вас,
не записывая ничего: `python -m pi seed --dry-run`.

Возвращаться к `seed` имеет смысл и позже — например, если снизили пороги в
`filters.toml` и не хотите получить всё, что стало подходить задним числом.

`detect` обходит все домены и раскладывает их по способам чтения:

| Состояние | Что значит |
|---|---|
| `shopify` | `/products.json` отдаёт весь каталог: цена, зачёркнутая цена, наличие, размеры, картинки |
| `jsonld` | обычный магазин с разметкой schema.org — читается по карточкам через sitemap (адрес sitemap берётся из `robots.txt`, затем из стандартных путей) |
| `blocked` | сайт отвечает, но не нам: Cloudflare, Kasada, 403, JS-челлендж |
| `tls` | хост жив, но сертификат не проходит проверку |
| `dead` | домен не резолвится или молчит |
| `unknown` | открывается, но цену со страницы товара не прочитать |

Список платформ не хранится руками: магазины переезжают, и захардкоженный список
устаревает молча. `python -m pi detect --broken` перепроверяет всё, что сейчас
не отдаёт данных, — это стоит делать после любой правки в способах чтения,
потому что прошлый вердикт выносил прошлый код.

Три вещи `detect` делает не самым очевидным образом, и каждая из них — вывод из
замера, а не предосторожность:

* **Витрину он не спрашивает.** `schema.org/Product` живёт на карточке товара, а
  не на главной. Пока вердикт выносился по главной, 45 магазинов числились «без
  структурных данных» — среди них BSTN, Consortium, Wood Wood, Blue Tomato. Из
  них читаемыми оказались двое; остальные рисуют цену джаваскриптом, и теперь так
  и написано в ошибке.
* **Сертификат, которому не хватает промежуточного звена, достраивается.**
  Ссылку на недостающее звено сертификат публикует сам (AIA); оно скачивается, и
  соединение повторяется с **полной** проверкой. Ничего не ослабляется: если
  достроенная цепочка не сходится к доверенному корню, магазин остаётся
  выключенным. Побочный эффект важнее самого исправления — восемь магазинов
  наконец сообщили свою настоящую беду (просроченный сертификат, чужое имя)
  вместо жалобы на отсутствующее звено.
* **Магазину, отвечающему 403, предлагается отпечаток браузера.** Подделка
  заголовков не помогает — замерено; совпадение идёт по TLS-рукопожатию.
  Зависимость `curl_cffi` опциональна: без неё такие магазины просто остаются
  выключенными.

**Первый обход каждого магазина ничего не присылает.** У нового магазина все
текущие распродажи выглядят свежими, и уведомления похоронили бы вас под
скидками полугодовой давности. Первый проход записывает цены как базовую линию,
а со следующего приходит то, что действительно изменилось.

## Обычная работа

```bash
python -m pi run                 # полный обход, отправка в Telegram
python -m pi run --dry-run       # то же, но сообщения печатаются в консоль
python -m pi run --collect-only  # только собрать цены, ничего не оценивать
python -m pi run --rescan        # переоценить всё после правки filters.toml
python -m pi health              # сводка: что собралось, что сломалось
python -m pi health --send       # прислать сводку в Telegram
python -m pi verify              # открыть самые давние карточки и убрать мёртвые
python -m pi prune               # выбросить историю старше 180 дней, сжать базу
python -m pi seed --dry-run      # сколько скидок проходит пороги прямо сейчас
python -m pi reindex             # пересобрать артикулы и нормализованные размеры
python -m pi reclassify          # заново определить марку, пол и тип у товаров
python -m pi bot                 # телеграм-бот; работает, пока не остановишь
python -m pi web                 # витрина в браузере: http://127.0.0.1:8000
python -m pi detect --broken     # перепроверить всё, что не отдаёт данных
```

Полезные ключи: `--stores a.com,b.com` ограничивает обход, `--limit N` — число
уведомлений за прогон.

### Витрина

Уведомления — это новости, а не каталог. В телеграм попадает только то, что
подешевело только что; всё остальное, что уже стоит со скидкой, там не
показывается никогда. На живой базе это 665 объявленных находок против 20 934
стоящих на полке.

`python -m pi web` открывает ту же полку страницей: всё, что сейчас со скидкой,
с фильтрами по размеру, полу, типу и марке, поиском и сортировкой. На каждой
карточке написано, когда магазин в последний раз подтвердил цену — это разница
между витриной и кладбищем.

Клик по товару открывает карточку: **кто ещё держит тот же артикул и почём**.
Это единственный вопрос, на который полка сама ответить не может, и это разница
между «магазин перечеркнул цифру» и «в соседнем магазине то же самое вдвое
дороже». Если товар дешевле у кого-то другого, карточка так и пишет — страница,
которая только хвалит то, что показывает, называется рекламой.

У 82% полки сравнивать не с чем, и там это сказано прямо. Ссылка вида
`?product=N` открывается сразу на карточке, чтобы находку можно было переслать.

**Детского на полке нет**, пока его не попросят кнопкой «Детское» в разделе
«Кому» (или `?kids=1` в адресе). Это 1 016 предложений из 33 738. Классификация
хранится в базе и только скрывается при показе — поэтому её ошибку видно и можно
исправить одной командой `pi reclassify`, не обходя магазины заново.

Сервер слушает только этот компьютер. Логина у него нет, поэтому `--host` с
любым другим адресом — осознанное решение, и его надо закрывать чем-то, у чего
логин есть.

Чтобы витрина открывалась кнопкой из бота, задайте адрес:

```
PI_WEB_URL=https://shelf.example.com
```

По `https://` Telegram откроет её внутри себя как мини-приложение, по `http://`
— обычной ссылкой в браузере. Без переменной кнопки просто нет.

### Избранное

На каждой карточке — сердечко, и на карточке товара, и в строках «пробить по
магазинам». Отмеченное собирается в свой список: кнопка ★ в шапке, или ссылка
`?favorites=1`, которую можно переслать.

Это не срез полки. Полка — то, что подешевело; вещь, за которой следят, обычно
стоит свою обычную цену, за этим за ней и следят. Поэтому в списке цена сейчас,
насколько она сдвинулась с того дня, когда вещь отметили, и «нет в наличии»
вместо пропажи из списка — это самая нужная строка там, где ждут возвращения
размера.

Отмеченное **проходит мимо всех порогов** в уведомлениях: мимо скидки в 30%,
мимо оценки, мимо лимита на магазин, мимо пола и размера. Повторно о нём
напишут, когда цена упадёт ещё на 2%, а не на 5%, как об остальном. Каждый
читатель отмечает своё: чужое избранное на ваши уведомления не влияет.

Записывать умеет только тот, кого назвал Telegram. Подпись `initData`
проверяется на каждый запрос, и исключений для локальной машины нет — иначе
`--host 0.0.0.0` мгновенно становится дырой. Отсюда **условие: сердечки
появляются только когда витрина открыта из Telegram как мини-приложение**, то
есть когда `PI_WEB_URL` начинается с `https://`. По `http://` страница
открывается обычной ссылкой, без подписи, и сердечек на ней нет вовсе — кнопка,
которая отвечает отказом, хуже её отсутствия.

Вне Telegram есть явный ключ, для отладки на своей машине:

```bash
python -m pi web --owner 123456789      # ваш Telegram user id
```

Он работает только на `127.0.0.1`: на адресе, доступном другим, он раздавал бы
всем чужое избранное.

### Товар, который перестали продавать

Магазин не сообщает, что снял вещь с продажи, — она просто исчезает из
каталога. Пока проект этого не замечал, полка была отчасти кладбищем: скидка
−93% на Wotherspoon у allikestore.com отдавала 404 две недели и всё это время
стояла первой карточкой.

Теперь между «пропал» и «удалить» три шага:

1. **Пропал.** Полное чтение каталога — то, где магазин перечислил всё, что у
   него есть, — ставит всем остальным его товарам дату пропажи. Карточки
   уходят с полки в тот же прогон.
2. **Ждёт.** Две недели (`delisted_grace_days` в `filters.toml`) строка лежит
   помеченной. Вернувшийся товар снимает пометку сам, при первом же чтении, и
   не теряет ни истории, ни избранного.
3. **Удалён.** `pi prune` удаляет то, что пролежало помеченным дольше срока, —
   вместе с вариантами и историей. Единственное необратимое действие в проекте,
   поэтому оно и ждёт две недели.

Бесплатный сигнал покрывает магазин, каталог которого читается за один проход,
— то есть почти все. Остальных — крупный магазин, который читается по частям, и
любой `jsonld` — спрашивают поштучно: `pi verify` открывает страницы товаров,
начиная с тех, на которые дольше всего не смотрели, и при равном возрасте с
самой большой скидки. То же самое делает каждый обычный прогон, 60 карточек за
раз (`--verify-budget`). 404 и 410 — «нет такого товара», 429 и 503 — «спроси
позже»: магазин, у которого выдался плохой день, не должен терять каталог.

Найденная так цена оценивается тем же прогоном, а не следующим: `pi verify`
проходит через обычный конвейер, у которого выключен только сбор.

Замер на живой базе (5 сентября, первый полный цикл): помечено 11 305 товаров
из 693 142 — 1,6% всей базы и 4,7% у магазинов, чей каталог успели прочитать
целиком. Тринадцать магазинов из 85 вышли за 10%, и это накопленное за месяцы
кладбище, а не ошибка: у bdgastore.com 1 461 товар в каталоге и 1 980
помеченных, ровно 3 441 в базе. Выборка из восьми помеченных карточек — восемь
404; выборка из восьми непомеченных — восемь 200.

### Спросить самому

Уведомления приходят, когда цена падает. Чтобы посмотреть, что подходит под ваши
условия прямо сейчас, не дожидаясь падения:

```bash
python -m pi find --brand nike,jordan --limit 20
python -m pi find --size US10,EU44 --max-price 200
python -m pi find --any-size --min-discount 60      # мимо фильтра размеров
python -m pi find --shop footdistrict.com
python -m pi find --kids                            # вместе с детским
```

Считает по всей базе, занимает минуту-другую, ничего никуда не отправляет и
показывает в том числе то, о чём уже присылали, — оно ведь всё ещё продаётся.

### Пробить вещь по всем магазинам

Полка показывает то, что подешевело. Это — вопрос обо всём каталоге, включая
95%, которые стоят обычную цену:

```bash
python -m pi price CW2288-111        # артикул с коробки
python -m pi price M2002RDB
python -m pi price "salomon xt-6"    # или просто название
```

По артикулу это один товар в разных магазинах, от дешёвого к дорогому, — тот
самый вопрос, на который витрина сама ответить не может: `same_article` ищет от
`product_id`, а идентификаторы у страницы есть только для того, что уже со
скидкой.

**Артикул и название — разные вопросы, и ответы на них выглядят по-разному.**
Артикул — это одна вещь у нескольких продавцов, и самая дешёвая из них есть
ответ. Название — это список разных вещей: «air force 1 07» находит 279 товаров,
и назвать самый дешёвый из них выгодной покупкой было бы враньём. Поэтому по
названию возвращаются сами товары, а не сравнение.

Честный ответ чаще всего — «один магазин»: из 105 707 артикулов в базе больше
чем у одного товара встречаются 17 936. Так и написано, а не подразумевается.

То же самое есть на витрине — строка «Пробить … по всем магазинам» под поиском,
ссылка вида `?lookup=CW2288-111`, эндпоинт `/api/lookup?q=` — и в боте: любое
сообщение, не начинающееся с `/`, читается как такой запрос.

### Следить за конкретной моделью

Список владельца, общий на всех, — `data/watchlist.txt`, по артикулу на строку.
Он и избранное складываются: файл про артикулы, избранное про товары и про
каждого читателя отдельно.

```
CW2288-111    # Nike Air Force 1 '07 White
M2002RDB      # New Balance 2002R
```

Такие товары проходят мимо порогов скидки, цены и оценки — и мимо лимита на
магазин. Вето они не отменяют: если эталонной цене взяться неоткуда, скидки нет,
как её ни жди. Это же верно и для избранного — 3% ниже собственного минимума за
30 дней дойдут, а цена, которая никуда не двинулась, нет.

## Автозапуск

```bash
cp systemd/* ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now price-intelligence.timer
systemctl --user enable --now price-intelligence-health.timer
systemctl --user enable --now price-intelligence-prune.timer

systemctl --user list-timers 'price-intelligence*'
journalctl --user -u price-intelligence -f
```

Бот — отдельный юнит, потому что он единственная долгоживущая часть проекта:
чтобы отвечать на нажатие кнопки, процесс должен уже работать.

```bash
systemctl --user enable --now price-intelligence-bot.service
journalctl --user -u price-intelligence-bot -f
```

Сбор идёт каждый час, сводка о здоровье — раз в сутки, чистка истории — раз
в неделю.

Каждый час обходятся не все магазины, а те, чья очередь подошла. Магазин,
давший находку за последние 30 дней, обходится каждый час; остальные — раз в
сутки. Сколько магазинов брать за раз, прогон решает сам: после чистого прогона
берёт на пять больше, после блокировки — на треть меньше, в пределах от 10 до
`PI_MAX_SHOPIFY_STORES`. Потолок сбора — квота на IP, и она не обходится
замедлением, поэтому частота обходов ничего не стоит, а размер среза стоит
всего. Перед установкой поправьте `WorkingDirectory` в юнитах, если проект
лежит не в `~/Projects`.

Чтобы таймеры работали при закрытой сессии: `loginctl enable-linger $USER`.

## Бот

Уведомления приходят сами; бот нужен, чтобы **спросить**. `/start` предлагает
пройти мастер из четырёх вопросов — пол, тип вещей, размеры, марки — или сразу
показать всё. Список идёт по десять позиций: цена, скидка, магазин и размер в
строку; цифра под списком открывает карточку с фото, наличием по размерам и
ссылкой в магазин.

Настройки бота живут в базе, а не в `filters.toml`, и это не мелочь:

- `filters.toml` отвечает на вопрос **«что считается скидкой»** — это свойство
  товара, одинаковое для всех, и на него ставится порог;
- профиль в базе отвечает на вопрос **«что показать этому человеку»**.

Поэтому размеры и марки в уведомлениях больше не отсекают, а **двигают планку**:

| | что делает |
| --- | --- |
| ваш размер | обычный порог, находка идёт выше в очереди |
| чужой размер | порог выше на 20 очков — «только если действительно дёшево» |
| названная марка | порог ниже на 10, находка идёт выше |
| незнакомая марка | приходит как обычно, ничего не теряется |
| «только женское» | единственный настоящий фильтр |

Жёсткий список марок ломается ровно на том, чего в нём нет: находка по марке, о
которой вы не подумали, не пришла бы никогда, и вы бы об этом не узнали.

## Настройка

Всё в `filters.toml` (см. `filters.toml.example`):

```toml
min_discount_pct = 30.0     # процент ниже опорной цены
min_saving_usd   = 40.0     # и одновременно экономия в долларах
min_price_usd    = 25.0
max_price_usd    = 2000.0
min_score        = 55       # 0-100
max_alerts_per_run = 15
fake_sale_days   = 21       # «было» не менялось столько дней → вечная распродажа

brands_allow = ["nike", "jordan", "new balance"]   # пусто = любые бренды
brands_deny  = []
sizes        = ["EU44", "US10", "US10.5"]          # пусто = любые размеры
```

После правки — `python -m pi run --rescan`, иначе изменения подействуют только
на товары, у которых цена сдвинется.

Скорость обхода — в `.env`:

```
PI_CONCURRENCY=8        # сколько магазинов обходится одновременно
PI_SHOPIFY_RATE=2.0     # общий бюджет запросов к Shopify, запросов в секунду
```

```
PI_MAX_SHOPIFY_STORES=45   # сколько Shopify-магазинов берётся за один прогон
```

Про лимиты Shopify стоит знать три вещи, все проверены замерами:

1. **Квота считается на IP.** Исчерпав её, вы получаете 429 от всех магазинов
   сразу, и форма запроса перестаёт иметь значение — последовательные запросы
   с паузой 2 с отказывают ровно так же, как восемь параллельных.
2. **Замедлением её не обойти.** Единственное, что помогает, — не упираться.
   Поэтому обход берёт порцию магазинов за прогон, а не все 138 сразу.
3. **Отпускает примерно за 3 минуты тишины.** Если кажется, что дольше, —
   скорее всего что-то продолжает слать запросы.

Магазины обходятся в порядке давности сбора, поэтому частичный прогон не
пропадает: следующий продолжит с того, до чего этот не дошёл. Четыре прогона в
сутки по 45 магазинов покрывают 138 с запасом.

Если в логе появилось `Shopify has blocked this IP` — обход это заметил и
прекратился сам, остальные магазины соберутся в следующий раз. Если это
повторяется каждый прогон, уменьшайте `PI_MAX_SHOPIFY_STORES`.

Размеры нормализуются приблизительно: `US 10.5` → `US10.5`, `EUR 44` → `EU44`,
голая `44` читается как EU44, голая `10` — как US10. Это верно чаще всего, но не
всегда, поэтому лучше перечислять несколько написаний своего размера.

## Объём и место на диске

Полный каталог 151 магазина — это порядка 2,7 млн вариантов и 800 МБ SQLite.
Это сами данные, а не мусор: чистка на свежей базе удаляет ноль строк. Со
временем историю подрезает `pi prune` (по умолчанию оставляет 180 дней, но
последнюю цену каждого варианта хранит всегда — иначе товар выглядел бы без
цены) и заодно выбрасывает товары без единой цены, а также те, что уже две
недели помечены пропавшими (см. «Товар, который перестали продавать»).

Уведомлений сверх `max_alerts_per_run` не теряется: прогон помечается, и
следующий пересчитывает всё заново, а не только изменившиеся цены. Без этого
хорошая скидка пропадала бы просто потому, что в тот же прогон пришли скидки
получше.

`data/sites.txt` — по домену на строку, `#` начинает комментарий. Домены,

## Устройство

```
pi/
├── config.py            .env для секретов, filters.toml для правил
├── db.py, schema.sql    SQLite: 10 таблиц, версия в PRAGMA user_version
├── fx.py                курсы валют (frankfurter.dev, без ключа) + суточный кэш
├── throttle.py          общий лимит запросов к Shopify (он на IP, а не на магазин)
├── sources/
│   ├── shopify.py       /products.json, пагинация ?page=N, валюта с витрины
│   ├── jsonld.py        schema.org/Product по карточкам из sitemap
│   ├── asos.py          собственный API магазина (см. ниже)
│   └── detect.py        определение платформы
├── taxonomy.py          марка, пол, тип и «это детское»
├── deals.py             три сигнала, оценка, дедупликация
├── notify.py            sendPhoto с подписью, откат на sendMessage
├── web.py, shelf.html   витрина: полка, карточка товара, поиск по каталогу
├── webauth.py           подпись Telegram — всё, что стоит перед записью
├── pipeline.py          собрать → оценить → отправить
└── cli.py
```

Заметки о поведении, которое легко нарушить при правках:

- **Валюта берётся с витрины**, а не угадывается по домену: `Shopify.currency.active`
  из HTML, затем страна из `/meta.json`. Домен `.com` в Берлине торгует в евро.
  Неизвестная валюта → цена отбрасывается, а не считается долларами.
- **Публичный `/products.json` листается через `?page=N`** и не отдаёт заголовок
  `Link` (в отличие от Admin API). Пагинация по `Link` молча обрезает каждый
  магазин на 250 товарах.
- **Лимит Shopify считается на наш IP по всей платформе, а не на магазин.**
  Поэтому все запросы к Shopify идут через один общий ограничитель
  (`pi/throttle.py`), а не через лимит на хост. Без него 16 параллельных
  магазинов выжигают общий бюджет: измерено — 58 из 138 магазинов потеряно за
  один обход, причём 429 держится минутами и `Retry-After` не приходит.
- **Точка истории пишется только при изменении** цены, зачёркнутой цены или
  наличия — иначе шестичасовой обход раздувал бы базу впустую.
- **Дедупликация по товару, а не по варианту.** Худи со скидкой в шести размерах
  — одна новость. Повторное уведомление только после падения ещё на 5%.
- **Адаптер под конкретный магазин — исключение, а не приём.** Три общих
  способа чтения (Shopify, schema.org, витрина) покрывают 180 магазинов из 310.
  ASOS не покрывается ни одним: в HTML карточки цены нет вообще, она приходит
  отдельным JSON-запросом. Для таких магазинов пишется адаптер вручную
  (`pi/sources/asos.py`), а `detect` спрашивает его первым — но **проверяет**,
  а не верит: адаптер, который перестал работать, должен выглядеть как
  сломавшийся магазин, а не как исправный.
- **У ASOS берётся не зачёркнутая цена, а минимум за 30 дней.** Магазин обязан
  публиковать эту цифру по европейскому закону о ценообразовании, и это ровно
  та величина, которую проект в остальных случаях считает сам по своей истории.
  Следствие намеренное: товар, простоявший месяц по цене распродажи, получает
  0% скидки — что и есть правда. Замер по живой выдаче: майка Nike стоит $10,
  минимум за 30 дней — те же $10, а зачёркнуто $20 (цена из декабря). По
  зачёркнутой это «половина цены», по факту — не новость.
- **Алерт записывается до отправки** и удаляется, если отправка не удалась:
  падение посреди отправки не должно приводить к повтору.
- **«Дочитали до конца» и «прочитали всё» — разные вещи.** `FetchResult.complete`
  значит только, что этот проход дошёл до конца того, что читал; пометить
  пропавшими всех, кого в нём не было, можно лишь по `FetchResult.enumerated` —
  а его ставит один Shopify и только когда проход начался с первой страницы.
  Проход, возобновившийся с сороковой и дошедший до конца, прочитал хвост
  каталога: списать по нему первые тридцать девять страниц значит стереть
  магазин. У `jsonld` неудачная страница неотличима от удалённой, у ASOS
  читаются только разделы распродажи — они не перечисляют ничего никогда.

## Ограничения

- **Цена в джаваскрипте — стена, а не недоделка.** У 44 доменов карточка товара
  открывается и содержит название и артикул, но цены в разметке нет вообще: ни
  JSON-LD, ни микроданных, ни Open Graph. Проверено поимённо, включая четыре
  магазина с микроразметкой — в ней только имя, артикул и картинка. Читать там
  нечего без браузера, рисующего страницу целиком.
- **19 доменов не пускают и с отпечатком браузера** (Foot Locker, JD, Zalando).
  Ещё шестеро пускают, но за дверью та же пустая комната из предыдущего пункта.
  Все помечаются `blocked` и попадают в сводку — вместо того чтобы молча
  возвращать ноль товаров.
- **У `jsonld`-магазинов нет зачёркнутой цены**: в schema.org её просто нет.
  Скидки там находятся по накопленной истории и по ценам других магазинов, то
  есть спустя несколько обходов.
- **Большой каталог читается по частям** — 400 карточек за прогон, дальше с того
  же места. В логе `(partial, resuming at 400)`. Крупный магазин покрывается за
  несколько дней.
- **Полный обход занимает порядка получаса.** Скорость упирается в общий лимит
  Shopify и в число карточек, а не в машину. Для шестичасового расписания это
  нормально.
- **Поиск по названию — это поиск, а не сравнение.** `LIKE` по названию и марке,
  триста товаров потолком, 150–400 мс на базе в 660 тысяч товаров. По артикулу
  ответ приходит за 3–9 мс, потому что там работает индекс. Слово без цифр
  никогда не считается артикулом, даже если какой-то магазин положил его в поле
  SKU: `nike` стоит там ровно у одного товара, и выдать этот магазин в ответ на
  вопрос о марке значило бы соврать уверенным тоном.
- **Избранное живёт только внутри Telegram.** Записывать на витрину может
  только тот, кого назвала подпись `initData`, а её страница получает, лишь
  когда открыта как мини-приложение, — то есть при `PI_WEB_URL` на `https://`.
  По `http://` витрина читается как раньше и сердечек на ней нет. Локально их
  включает `pi web --owner <id>`, и только на `127.0.0.1`.
- **Цена «на момент отметки» — не цена покупки.** Если в тот день всё было
  распродано, за точку отсчёта берётся последняя известная цена магазина, в
  каком бы состоянии её ни видели. Она показывается только когда выше нынешней,
  и строгое сравнение в уведомлении остаётся прежним — минимум за 30 дней,
  рыночная цена, РРЦ.
- **Поштучная проверка идёт медленно.** 60 карточек за прогон против 33 тысяч
  на полке — полный круг занял бы больше трёх недель, если бы полагаться только
  на него. Он и не рассчитан на это: почти всё закрывает бесплатный сигнал от
  полного чтения каталога, а поштучно спрашивают там, где его не бывает.
- **Товар, снятый с продажи, не «уценяется», а исчезает.** Проект не отличает
  «распродано» от «снято»: и то и другое выглядит как отсутствие в каталоге. Для
  полки разницы нет — карточку, которую нельзя купить, показывать нельзя, — но
  история такого товара удаляется через две недели вместе с ним.
- **Сопоставление по артикулу не различает состояние товара.** Пара «без
  коробки» сравнивается с ценой такой же пары в коробке, и разница выглядит
  скидкой. Обычно это видно по названию в уведомлении.
- **Детский размер неотличим от взрослого после нормализации.** `5Y` становится
  `US5`, то есть детская пятёрка и женская пятёрка попадают в одну ячейку. Из-за
  этого размер не участвует в определении детского вовсе — признаком служат
  слова в названии и категория, — и фильтр по `US5` показывает и то и другое.
- **Нормализация размеров приблизительна.** `US 10.5` → `US10.5`, `X-Large` →
  `XL`, голая `44` читается как EU44, а голая `10` — как US10. Чаще всего верно,
  но не всегда, поэтому в `sizes` лучше перечислить несколько написаний своего
  размера. Нормализованное значение хранится в базе, поэтому после правки правил
  нужен `pi reindex` — иначе старые записи останутся со старым написанием.
